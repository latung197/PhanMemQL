# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

S-ERP: a Vietnamese ERP made of two apps plus user docs.

- `Frontend/`: React 19 + TypeScript, Vite 6, Tailwind v4, served by an Express dev server (`server.ts`) on `http://localhost:3000`. `server.ts` also hosts `/api/gemini/analyze` (AI assistant, needs `GEMINI_API_KEY`).
- `ServerService/`: .NET 10 Web API (EF Core + Dapper, PostgreSQL) on `http://localhost:2512`.
- `docs/`: guides in Markdown (source) + Word copies, in folders by function: `kho/` (inventory: receipt, stock ledger, warehouse catalog), `mua-hang/` (purchasing: request → order → receipt, projects, project cost report), `tai-chinh/` (accounting: chart of accounts of Circular 200, tax accounts), `ban-hang/` (sales: customer groups, customers, price lists), `he-thong/` (permissions, menu), `phat-trien/` (framework guides: add a catalog, table references, lost updates), `cong-cu/` (Markdown → Word scripts). Index and conventions: `docs/README.md`. New guides go in the folder of their function, never directly in `docs/`.

**The frontend is the source of truth.** Function codes, data shapes and API response types follow `Frontend/src/types/index.ts` (`UserProfile`, `RoleDefinition`, `ActionPermissions`, `CompanyUnit`, `SystemNotification`) and the settings sections in `Frontend/src/services/systemSettingsService.ts`. The backend adapts to match.

UI text, error messages (`{ message }` from the API) and docs are written in **Vietnamese**.

Multi-language (guide with every flow, the code patterns and the list of functions already / not yet translated: `docs/phat-trien/da-ngon-ngu.md`): languages are the backend catalog `sys_language` (Settings › Ngôn ngữ), each user has an own language (`sys_users.language`, null = default) and the frontend sends it as `Accept-Language`. Backend user texts live in `ServerService/Core.Application/Common/Localization/Messages.{vi,en}.json`: throw `new BusinessRuleException("module.key", args)` (never a sentence), Guard labels are `field.*` keys, and `MessagesTests` fails on a missing key or a Vietnamese sentence in a `throw`. Missing texts fall back to Vietnamese. Only the shared parts and Settings are being translated for now (Inventory later, when it is redeveloped).

## Commands

Frontend (run in `Frontend/`; there is no JS test runner or linter beyond `tsc`):

```bash
npm run dev          # tsx server.ts → http://localhost:3000 (Vite middleware mode)
npm run lint         # tsc --noEmit (type check)
npm run build        # vite build + bundle server.ts to dist/server.cjs
npm run export-seed  # regenerate ../ServerService/Core/SeedData/seed.json from src/mock
npm run check-policy # check utils/documentPolicy.ts against the backend test cases
npm run check-menu   # check the sidebar logic (toTree, rights, hide flags) against Core/SeedData/menu.json
npm run check-label  # check the stock label code (MATERIAL#LOT#LOCATION) encode / parse
```

`.env.local` (copy from `.env.example`): `VITE_API_URL` (defaults to `http://localhost:2512`), `GEMINI_API_KEY`.

Backend (run in `ServerService/`; xUnit tests):

```bash
dotnet build Core.sln
dotnet test tests/Core.Tests/Core.Tests.csproj
dotnet test tests/Core.Tests/Core.Tests.csproj --filter "FullyQualifiedName~PermissionMatrixTests"
dotnet run --project Core/Core.csproj --urls http://localhost:2512   # set ASPNETCORE_ENVIRONMENT=Development
```

Local secrets live in `ServerService/Core/appsettings.Local.json` (gitignored): `ConnectionStrings:CoreContext`, `Tokens:Key` (≥32 chars), `Seed:DemoData`, `Seed:DefaultPassword`, `Seed:AdminPassword` (Development only; resets `admin`'s password on every start).

Database: run every script in `ServerService/sql/postgresql/` **in filename order** (`00-helpers.sql` first; `psql` may not be on PATH, e.g. `C:\Program Files\PostgreSQL\16\bin`). Scripts are idempotent and also migrate older data. There are no EF migrations; schema changes go into a new or existing `NN-*.sql` script.

In Development the backend serves Swagger UI at `http://localhost:2512/swagger` (every endpoint with the rights it needs, JWT via **Authorize**; `POST /api/auth/login` gives the token); it is off elsewhere.

`.claude/launch.json` defines `backend` (port 2512, Development) and `frontend` (port 3000) for the preview tools.

### Function codes tie everything together

A `SubMenuKey` (e.g. `inv_receipt`) is the shared key for menu, route, permissions, notifications and approvals. A new function is declared in:
- Frontend: `src/types/index.ts` (`SubMenuKey`) and **`src/config/functions.ts`** (`FUNCTION_REGISTRY`: category, hash path, label, kind — typed `Record<SubMenuKey, …>`, so a missing entry is a compile error). Routes (`config/router.ts`), breadcrumbs (`utils/navigationHelper.ts`) and the permission matrix (`permissions/permissionCatalog.ts`) are derived from it. Then a node in `ServerService/Core/SeedData/menu.json` (the sidebar comes from `sys_command` via `GET /api/menu`, which returns only the functions the user may View (cached tree cut per user by `MenuFilter`, tested in `MenuFilterTests`). The structure (names per language, icon, order, group of a function, new groups) is edited only by the super admin, one account named in `Security:SuperAdmin` (default `admin`, must also be ADMIN; policy `SuperAdmin`, `IMenuService`, `MenuRules`, tab **Cấu trúc menu** of Settings › Quản lý menu, every change audited as `sys_menu`/`menu`); functions are never added or removed there; at startup the seeder only inserts nodes the database has no menu row for, never overwrites existing ones; `MenuSeedFileTests` keeps the file and `FunctionCatalog` in step; a new icon goes into `components/common/DynamicIcon.tsx`) and a `case` in the parent `*Module.tsx` (Settings: `renderScreen` in `SettingsModule.tsx`; settings screens are opened from the sidebar only, no tab bar).
- Backend: `Core.Application/Common/Permissions/FunctionCatalog.cs` (API auto-inserts missing codes into `sys_command` on startup). Vouchers also go in `Common/Documents/VoucherCatalog.cs`, which gives them a number series, the voucher special rights and a place in approval rules.
- Always navigate with `navigateTo` / `openFunction` in `App.tsx` (keeps the URL hash in sync); never set the active sub-menu state directly.

### Permissions

- Each function has 7 actions: `view / create / edit / delete / approve / print / export` (create = add, copy, import Excel; edit = change saved records; export = data to a file). Endpoints: `POST` → `PermissionAction.Create`, `PUT` / saving settings → `Edit`; submitting a voucher needs `Create` or `Edit`. Legacy flags map 1:1 (`can_add`, `can_edit`, `can_print`, `can_export`); `ActionPermissionsJsonConverter` still reads old `createEdit` / `printExport` JSON (seed, backups). Frontend screens: add button / import → `perms.create`, edit → `perms.edit`, `onExportExcel` only when `perms.export`, print → `perms.print`. Special rights are `{function}:{CODE}` (e.g. `inv_receipt:VIEW_PRICE`), declared in `SpecialRightCatalog.cs`. **Voucher status rights are per company unit**: `ST_PENDING / ST_APPROVED / ST_POSTED / ST_CANCELLED / ST_UNPOST` (a voucher that never posts has no `ST_POSTED` / `ST_UNPOST`: `VoucherStatusCatalog.NonPosting`) are stored with the unit in the code, `{function}:ST_POSTED@DVCS01` (`SpecialRightCatalog.UnitKey` / `SplitUnit` / `KeysFor(units)`; `PerUnit` flag of the definition), so `sys_role_right` / `sys_user_right`, `GrantGuard`, audit and `specialRights` work unchanged; `DocumentActor.For(..., unitCode)` keeps only the rights of the voucher's unit, administrators hold them for every active unit. A right for a later status includes the earlier steps (`DocumentActor.Reaches`: Pending < Approved < Posted) and a user may save a voucher at any status their rights reach (`DocumentStatusPolicy.CheckTarget`). Frontend: `hasStatusRight` / `reachesStatus` read `user.ma_dvcs`. The statuses themselves are fixed by the code; a unit renames them and may switch off "Chờ duyệt" (a voucher then skips approval, `IDocumentApprovalService.ApproveWithoutFlowAsync`) in Settings › Trạng thái chứng từ (`sys_voucher_status`, only changed statuses have a row; `IVoucherStatusService`, `GET /api/voucher-statuses/current` for the screens, `services/voucherStatusService.ts`, script `43-voucher-status.sql` also converts the old POST / UNPOST / CANCEL / EDIT_* rights); guide `docs/he-thong/trang-thai-chung-tu.md`.

Voucher detail grids (the columns under a voucher, one grid per tab: `PNK_ITEMS`, `PNK_BOM`...) are configured system-wide in `sys_voucher_grid` + `sys_voucher_grid_column` (script `49-voucher-grids.sql`, Settings › Cấu hình lưới chứng từ, function `sys_voucher_grid`, `VoucherGridService`, `GET/PUT /api/voucher-grids`, rules `VoucherGridRules`): order, headers vi/en, width, decimals, hide / show (required columns cannot be hidden) and `pin_count` (first N visible columns sticky). ### Backend structure

Clean architecture, one-way deps `Core → Core.Infrastructure → Core.Application → Core.Domain`. In each layer, shared code is in `Common/` and features in `Modules/<Module>/`:
- `Core.Domain`: entities (`AuditableEntity` for `sys_*` audit columns).
- `Core.Application`: DTOs + service interfaces, pure rules (`PermissionMatrix`, `ApprovalRuleEngine`), exceptions (`BusinessRuleException`→400, NotFound→404, AuthenticationFailed→401, Forbidden→403, mapped to `{ message }` by `AppExceptionFilter`).
- `Core.Infrastructure`: `CoreContext` (EF), `UnitOfWork`, `SqlExecutor` (Dapper), services, `DatabaseSeeder`; register services in `DependencyInjection.cs`.
- `Core`: thin controllers, auth policies, `AddApi` (JWT, CORS `Cors:AllowedOrigins`, rate limiting). Can run as a Windows service.
- `_legacy/` is pre-refactor code, not in the solution; don't edit or reference it.

Shared building blocks for vouchers (see the "Khung lưu một phiếu" snippet in `ServerService/README.md`): `IFiscalPeriodService.EnsureDateOpenAsync` (month locks per unit + data entry start date), `IVoucherNumberService.NextAsync` (atomic via `VoucherNumbering/Sql/NextNumber.sql`, call inside the save transaction), `IExchangeRateService.GetRateAsync`, `DocumentStatusPolicy`, `IDocumentApprovalService`.

Settings storage: values nothing else references live as JSON sections in `sys_setting` (`SystemConfigSections`); anything referenced by other data (currencies, rates, departments, month locks, number series) has its own table. Users link to departments by `department_code` (the `department` column keeps the name for display); approval rules of type DEPARTMENT store the code.

Data access rules:
- **CRUD via EF Core**; **reports, calculations, ledger posting via raw SQL** through `ISqlExecutor`. SQL files live in `Core.Infrastructure/Modules/<Module>/Sql/<Name>.sql` (embedded resources), loaded with `SqlScripts.Get("<Module>", "<Name>")`. Always parameterize (`@name`); snake_case columns auto-map to PascalCase.
- Wrap EF save + raw SQL posting in `IUnitOfWork.ExecuteAsync(...)` so both share one transaction.

Database conventions (enforced by `TablesAndColumnsFollowNamingConvention` test):
- `sys_*` for system tables, `erp_*` for business tables; `snake_case` table/column names.
- Every `erp_*` entity inherits `ErpEntity` (`created_at`, `created_by`, `updated_at`, `updated_by`; timestamptz UTC, user ids), filled by `CoreContext` on save, never by callers; test `BusinessTablesHaveRecordStamps`. DTOs carry them as `stamp` (`RecordStampDto` via `RecordStamps.ForAsync`, names looked up in one query); frontend `recordStampColumns(t)` / `<RecordStampLine>` (`components/common`). Legacy `sys_*` tables keep `createtime` / `createid` / `updatetime` / `updateid`.
- Lost updates: records edited in forms implement `IVersioned` (`uint Version`, every `ErpEntity` has it), mapped by `CoreContext` to PostgreSQL's `xmin` as concurrency token (no SQL column needed; test `VersionedRecordsUseXminAsConcurrencyToken`). DTOs return `version`, save requests take `uint? Version = null`, and `UpdateAsync` calls `db.ExpectVersion(entity, request.Version)` right after loading (`touch: true` when a save may only change child rows: roles, user permissions / units). A stale version → `ConflictException("record.changed")` → HTTP 409 (also for `DbUpdateConcurrencyException`). Frontend: `useCatalog.save` sends `existing.version` and reloads on 409; other screens pass `version` from the loaded record. `ConcurrencyContractTests` fails when a service `UpdateAsync` lacks the request / DTO `Version` or the `ExpectVersion` call (exemptions with a reason in its `Exempt` list). Guide: `docs/phat-trien/chong-ghi-de.md`.
- References between tables (no foreign keys): every column named `*_code` is declared on its entity with `[References<TargetEntity>]` (`Optional = true` when it may be empty, `BlocksDelete = false` for translation / history tables) or `[NotReference(reason)]` (tax code, function code...); the column name ends with the target table name without `erp_` / `sys_` (`uom_code`, `from_uom_code`; only `unit_code` is legacy) and has an index starting with it (script `24-table-ref.sql` shows the pattern). `CatalogService` then refuses to delete a row other tables still use (`record.inUse`, naming the tables via `table.<name>` messages) and checks on save that a referenced code exists (`ref.notFound`); hand-written services call `db.EnsureNotInUseAsync<TEntity>(code, name, ct)` (`Core.Infrastructure.Common.References`). The map is written to `sys_table_ref` at every start and joined with the real columns in the view `sys_v_columns`; `TableReferenceTests` guards it. Guide: `docs/phat-trien/tham-chieu-danh-muc.md`.
- **Shared column types (domains)**: new columns use the domains of `sql/postgresql/00-helpers.sql`, never a bare `varchar(N)` / `numeric(P,S)`: `ud_code10|20|30|50|64` (codes), `ud_text100|200|300|500|1000` (names, notes), `ud_dec18_2` (money), `ud_dec18_4` (quantity, unit price / cost), `ud_dec9_4` (percent), `ud_dec20_8` (conversion factor), `ud_status`, `ud_user_id`, `ud_smallint|int|bigint|bool|date|timestamptz`. The name carries the definition, so a longer varchar is a new domain, not an `ALTER DOMAIN`. A `*_code` column pointing to a catalog is exactly as long as that catalog's code (`ColumnLengthTests`: material code 50, unit of measure 20, lot number 30, voucher code 64). Script `65-shared-domains.sql` moved the existing columns (idempotent); `npm run tao-danh-muc` writes domains. Guide: `docs/phat-trien/them-danh-muc.md` ("Kiểu cột dùng chung").
- Catalog columns: the key and display name of a catalog are always `code` and `name` (the shared framework relies on them); a column pointing to another catalog is `<target table>_code` (`uom_code`, `warehouse_code`); Vietnamese labels live in `locales/*`, not in column names (no `ma_vt` / `ten_vt`).
- **No foreign keys.** Link by indexed code/ID columns; services validate references and block deleting in-use rows. Relationships in `CoreContext` exist only for EF joins.
- `00-helpers.sql` provides `sys_rename_table`, `sys_rename_column`, `sys_rename_constraint`, `sys_drop_foreign_keys` for migration-style scripts.

Seeding: every startup inserts missing function codes, number series for new `VoucherCatalog` entries and a base currency (VND) if none. With an empty `sys_users`, `Seed:DemoData=true` loads `Core/SeedData/seed.json` (exported from the frontend mocks via `npm run export-seed`, incl. `mock/initialSettingsData.ts`); otherwise `Bootstrap:AdminPassword` (≥12 chars) creates only the admin and one unit.

Change log: `sys_audit_log` is shared by every function and filled **automatically**: `CoreContext.SaveChangesAsync` runs `AuditTrail`, which logs every insert / update / delete of an entity marked `[Audited(function, objectType, Label = "...", SoftDelete = ...)]` (field before → after, same transaction; only for a signed-in user). Every entity must say `[Audited]` or `[NotAudited(reason)]` (`AuditDeclarationTests`); use `[AuditIgnore]` for secrets / preferences, `[AuditField]` to rename legacy columns, `[AuditJson]` for JSON columns, `[AuditedChild]` for list tables. By hand via `IAuditLog` only for what EF cannot see or needs business meaning: `Attach(entity, changes)` (e.g. names for ids), `RecordAsync(AuditEntry)` for permissions (effective rights, `UserAccessAudit`), password reset/change, approval actions, raw SQL / `ExecuteUpdate`. Shown only on Settings › Nhật ký thay đổi (`sys_audit_log`, `modules/settings/AuditLogView.tsx`, filters from `GET /api/audit-logs/filters`), never on the functions' screens; labels `audit.*`.

Change log retention: Settings › Nhật ký thay đổi › Lưu trữ (`GET/PUT /api/audit-logs/settings`, section `auditLog` in `sys_setting`, 0 = forever); `AuditLogCleanupService` deletes older rows in batches twice a day and leaves one `PURGE` row (by "system").

Database errors: `DatabaseErrors` (used by `AppExceptionFilter`) turns any unique violation into 409 `record.duplicate` naming the field (`dbfield.<column>` message keys) and value (Npgsql `IncludeErrorDetail`), deadlocks into 409 `record.busy`, and data the column cannot take into 400 (`db.numberOutOfRange` for a number too large for numeric(18,x), `db.badCharacter` for NUL in a text or a filter of the query string, `db.textTooLong`). Services still pre-check for specific messages.

Stock ledger (sổ kho): every voucher that moves stock posts through `IStockLedger` (`PostAsync` / `UnpostAsync`, `Core.Infrastructure/Modules/Inventory/Stock/`), never with its own SQL. `erp_stock_movement` is the append-only journal (signed quantity in the material's base unit, value in base currency; unposting writes reversal rows via `reversal_of_id`, posting again raises `posting_seq`); three balance tables are moved in the same transaction: `erp_stock_balance` (unit + warehouse + material: quantity and value), `erp_stock_lot_balance` (+ lot, only materials with `track_lot`) and `erp_stock_location_balance` (+ location, only `track_location`); they always equal the sum of the journal (`GET /api/inventory/stock/verify` checks, `POST .../rebuild` repairs; both under `inv_calc_instant_stock`). Rules: stock out is valued at the warehouse moving average, a balance row is locked `FOR UPDATE` before it is read (two vouchers cannot take the same stock), negative stock is refused unless the unit's `allowNegativeStock` parameter is on, lines are applied in material / lot / location order, stock in opens a missing lot (an expiry material then needs `LotExpDate`), a blocked lot takes and gives nothing and an expired lot cannot be issued, a line unit other than the base unit converts through `erp_uom_conversion`. The balance and journal tables are `ErpEntity`s only for reading and for `[References]` (so a material, lot, location or warehouse with stock history cannot be deleted); they are written with SQL, never EF. Reading: `GET /api/inventory/stock/balances?level=warehouse|lot|location` and `/movements` (`inv_report_stock`, values need its `VIEW_COST`). Goods receipts post in (value from the voucher) and goods issues post out (value computed by the ledger) through it (item lines only; lot / position typed on a line only count for materials that track them, until the receipt picks them from the catalogs). A voucher save request carries an optional `TargetStatus` (Draft, Pending, Approved1, Approved2, Approved, Posted): the service saves the draft, then runs the steps in the same transaction as far as the user's rights reach (an approval status needs its right in the unit and, for the intermediate levels, the level switched on: `IDocumentApprovalService.ApproveDraftToAsync`; Posted also the `ST_POSTED` right of the unit; Pending needs the step switched on). **Approving and posting are status rights, and the approval levels are the voucher statuses** (guide `docs/he-thong/duyet-nhieu-cap.md`, Word copy `Duyet-nhieu-cap.docx`, summary in `trang-thai-chung-tu.md`; script `63-approval-levels.sql`): the life cycle is Draft → Pending → Approved1 → Approved2 → Approved → Posted (or Cancelled); the two intermediate levels ("Duyệt cấp 1 / 2", rights `ST_APPROVED1` / `ST_APPROVED2` per unit) are off until a unit switches them on in Settings › Trạng thái chứng từ (`VoucherStatusCatalog.EnabledByDefault`, `IVoucherStatusService.ApprovalLevelsAsync`), so the number of approval levels = the approval steps the unit uses (max 3; approval rule levels 1–3 only pick whom to notify, `ApprovalResolver`); each step row of `sys_document_approval` keeps its `target_status`. Approving (`ApproveNextAsync`, the `approve` branch of every voucher service; the approval service sets the voucher status) takes the voucher to the highest level in use the user reaches (a later right includes the earlier levels, own vouchers too) and notifies the next level; reject needs the right of the level waiting; `DocumentStatuses.InApproval` (Pending / Approved1 / Approved2) is what withdraw and the cancel guard test, never `== "Pending"`; frontend labels `voucherStatusLabels.ts` (`canApproveVoucher`, `approvalLevelOptions`). `ST_POSTED` posts a draft / in-approval / approved voucher (the missing levels are recorded first, `IDocumentApprovalService.ApproveToEndAsync`); the "Duyệt" column of the matrix no longer decides (it only opens the approval screens); any refusal rolls the whole save back; the "Trạng thái" field of the form is the choice (`saveStatusChoices` in `SaveStatusSelect.tsx`). A posted voucher (goods receipt / issue, transfer issue / receipt) can be changed or deleted by a user with the per-unit right `ST_EDIT_POSTED` (`PostedEdit.EnsureAsync`): an update goes through `IStockLedger.ReplaceAsync` (reverse the old posting and post the new one in one transaction, negative stock checked only on the end result of the slots touched, `stock.insufficientAfterChange`), a delete unposts first (strict check); a transfer issue with live receipts is refused; guide `docs/kho/sua-xoa-phieu-da-ghi-so.md`. Deleting a receipt / issue header fires the trigger of script `41-voucher-delete-trigger.sql` (`erp_voucher_delete_cleanup`): it deletes the voucher lines, refuses when the voucher is still posted and, for an unposted voucher (its journal rows net to zero), also deletes those journal rows, so the balance tables stay equal to the journal. A cancelled voucher can be restored to Draft (`DocumentAction.Reopen`, endpoint `POST .../{id}/reopen`, button "Khôi phục", right `ST_CANCELLED`, month open, lines that follow another voucher must still fit it: `EnsureLinksStillFitAsync` in each voucher service, `reopen.*` messages; policy mirror + `DocumentPolicyCases.json`); the list buttons Hủy / Bỏ ghi sổ ask for confirmation first. A route parameter must never be called `action`, `controller`, `area`, `handler` or `page` (reserved: the route never matches). Dev data: all 2026 months of DVCS01 are locked, so test vouchers with a 2027 date.

Cache: `IAppCache` (memory, one instance) with table dependencies; `CacheInvalidationInterceptor` drops entries whenever CoreContext writes their tables (and again on commit / rollback); read through `db.CachedAsync(cache, key, tables, factory, ct)`, which bypasses the cache inside an open transaction. Cached: per-user access snapshot in `PermissionService` (token check, matrix, rights, units), active units, settings per unit, active languages, catalog lookups (`LookupService`), and the whole lists of catalogs not yet moved to server paging (a server-paged list is not cached: every query differs, and the paged query is cheap). Never cache stock, balances, voucher numbers, month locks. Dapper writes must call `cache.InvalidateTables`.

Logs / monitoring: Serilog (`Serilog` section; console + `Core/logs/erp-*.log`, 30 days), one line per request with UserId / UnitCode / ClientIp / RequestId (`X-Request-Id` header), slow requests (`Monitoring:SlowRequestMs`) and slow SQL (`SlowQueryInterceptor`, `Monitoring:SlowQueryMs`) as warnings; `GET /health` (database) and `/health/live`.

Notifications: `NotificationStream` keeps SSE connections in memory (single-instance only); the server only sends `notification`/`sync` signals and the client refetches. Frontend also polls every 3 minutes. `NotificationCleanupService` purges old rows every 12h.
